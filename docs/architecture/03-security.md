# Безопасность и шифрование

## Цель безопасности

Система должна быть устроена так, чтобы backend, база данных, Redis, MinIO и TURN-сервер не могли прочитать переписку или расшифровать звонки. Компрометация сервера не должна автоматически раскрывать историю сообщений в plaintext.

## Threat model для MVP

Защищаемся от:

- перехвата сетевого трафика;
- чтения сообщений администратором backend/БД;
- утечки дампа PostgreSQL;
- утечки объектов MinIO;
- прослушивания TURN-релея;
- повторной отправки старых запросов;
- brute force логина.

Пока не решаем полностью:

- компрометацию устройства пользователя;
- malware на телефоне;
- подмену приложения;
- сложные атаки на supply chain;
- полноценную анонимность metadata.

## Шифрование сообщений

Требование: сервер хранит только ciphertext.

Рекомендуемая модель:

- У каждого устройства есть долгосрочный identity key pair.
- У каждого устройства есть signed pre-key.
- Устройство публикует набор one-time pre-keys.
- Отправитель получает key bundle получателя с backend.
- Клиенты устанавливают E2EE-сессию.
- Каждое сообщение шифруется на клиенте.

Практичный путь реализации:

1. Для MVP не писать собственную криптографию низкого уровня.
2. Использовать готовую реализацию Signal-подобного протокола, если она подходит для Flutter.
3. Если готовая библиотека не подходит, на первом этапе использовать libsodium/X25519 + Double Ratchet только после отдельного проектирования и тестирования.

Запрещено:

- отправлять plaintext на backend;
- хранить приватные ключи в backend;
- логировать ciphertext payload полностью без необходимости;
- использовать самописный алгоритм шифрования;
- переиспользовать nonce для AEAD.

## Шифрование вложений

Фото и видео шифруются до загрузки.

Flow:

1. Клиент генерирует случайный file key.
2. Клиент шифрует файл локально через AEAD, например XChaCha20-Poly1305 или AES-GCM.
3. Зашифрованный файл загружается в MinIO.
4. File key шифруется отдельно для получателей чата.
5. Backend хранит только encrypted file и encrypted key envelopes.

MinIO не должен видеть plaintext.

## Безопасность звонков

Звонки делаются через WebRTC:

- media шифруется DTLS-SRTP;
- signaling идёт через backend по WSS;
- STUN/TURN используется только для установки соединения;
- TURN-релей не должен иметь ключей для расшифровки media stream.

Для дополнительной защиты групповых звонков в будущем можно добавить insertable streams / E2EE поверх WebRTC, особенно если будет использоваться SFU.

## Авторизация

Пользователи создаются заранее. Публичной регистрации нет.

Требования:

- пароли хранить через Argon2id;
- access token — короткоживущий;
- refresh token — долгоживущий, но хранится на сервере только hash;
- refresh token rotation;
- logout инвалидирует refresh token;
- rate limit на login;
- блокировка или задержка при множественных ошибках входа.

## Transport security

- Production API только через HTTPS/WSS.
- HTTP допустим только локально в dev.
- CORS ограничить конкретными origin.
- Docker Compose для локальной разработки может работать без TLS, но production-конфигурация должна быть TLS-terminated через reverse proxy.

## Секреты

В git нельзя хранить:

- production JWT secrets;
- database passwords;
- S3 credentials;
- TURN credentials;
- приватные ключи пользователей;
- реальные seed-пароли.

В git можно хранить:

- `.env.example`;
- dev-only тестовые значения, явно помеченные как небезопасные;
- seed users без реальных паролей или с dev-only паролями.

## Логи

Разрешено логировать request id, user id, device id, chat id, message id, размер attachment и технические ошибки.

Запрещено логировать plaintext сообщений, пароли, refresh/access tokens, приватные ключи и полные encrypted payload без необходимости.

## Backup и восстановление

Для MVP: backup PostgreSQL и MinIO bucket. Redis можно не backup-ить, если там только временное состояние.

Важно: backup тоже содержит ciphertext и metadata, но не должен содержать приватные ключи клиентов.

## Проверки безопасности перед релизом MVP

- Проверить, что backend API не принимает plaintext message field.
- Проверить, что upload в MinIO происходит только после локального шифрования на клиенте.
- Проверить, что refresh token хранится hash-ом.
- Проверить rate limit на login.
- Проверить, что WebSocket требует авторизацию.
- Проверить, что пользователь получает только свои чаты.
- Проверить, что участник не может читать чужой чат по ID.
- Проверить, что TURN credentials ограничены сроком жизни.
- Проверить, что debug logs выключены в production.
