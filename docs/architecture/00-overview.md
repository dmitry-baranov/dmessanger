# Общая архитектура dmessanger

## Цель

Сделать приватный мессенджер для Android с небольшим числом пользователей. На первом этапе целевая нагрузка — до 10 активных пользователей одновременно. Регистрации нет: пользователей создаёт администратор заранее, пользователь входит по логину и паролю.

Продуктовая ориентация: простой UX в стиле Telegram — список чатов, экран диалога, медиа-вложения, звонки, групповые чаты.

## Основные возможности

- Авторизация по логину и паролю.
- Список личных и групповых чатов.
- Отправка и получение текстовых сообщений.
- Отправка фото и видео.
- История сообщений.
- Статусы доставки: отправлено, доставлено, прочитано.
- 1:1 аудио/видео звонки.
- Групповые аудио/видео звонки.
- Push-уведомления на Android.
- Шифрование переписки и звонков так, чтобы backend не мог читать содержимое.

## Основные проектные решения

Монорепа:

```text
dmessanger/
├── mobile/                    # Flutter Android app
├── server/                    # Backend-монолит
├── deploy/
│   └── docker-compose.yml     # Backend + инфраструктура
└── docs/
    └── architecture/
```

Backend остаётся одним приложением. Инфраструктурные сервисы поднимаются рядом через Docker Compose:

- PostgreSQL — пользователи, чаты, участники, метаданные сообщений, сессии.
- Redis — краткоживущие состояния: online presence, WebSocket-сессии, rate limit, временные call states.
- MinIO — локальное S3-совместимое хранилище для фото и видео.
- COTURN — TURN/STUN сервер для WebRTC-звонков через NAT.
- Backend app — REST API, WebSocket, signaling для звонков, админские операции.

## Выбранный стек

### Mobile

- Flutter.
- Android как первая платформа.
- State management: Riverpod или Bloc. На старте предпочтительнее Riverpod из-за меньшей шаблонности.
- Локальная БД: Drift или Isar. На старте предпочтительнее Drift, потому что SQL-схема проще контролируется.
- HTTP: Dio.
- WebSocket: отдельный persistent connection service.
- WebRTC: `flutter_webrtc`.
- Secure storage: `flutter_secure_storage`.

### Backend

Базовый вариант: Kotlin + Spring Boot.

Причины:

- один backend-монолит без микросервисной сложности;
- хорошая поддержка REST, WebSocket, PostgreSQL, Redis;
- понятная сборка Docker-образа;
- строгая типизация для протоколов и моделей;
- легко расширять при росте проекта.

Если при реализации окажется важнее минимальный runtime и простая поставка одним бинарником, backend можно заменить на Go. Архитектурно это не меняет границы системы.

## Высокоуровневые компоненты

```text
Flutter Android app
        |
        | HTTPS REST
        | WSS WebSocket
        | WebRTC media
        v
Backend monolith  ---> PostgreSQL
        |          ---> Redis
        |          ---> MinIO
        |
        +---------> COTURN для WebRTC relay
```

## Ключевые принципы

1. Backend не должен иметь доступ к plaintext сообщений.
2. Медиа-файлы хранятся в MinIO только в зашифрованном виде.
3. Звонки идут через WebRTC с DTLS-SRTP. TURN может ретранслировать трафик, но не должен иметь возможности расшифровать media stream.
4. Пользователи создаются заранее. Саморегистрации нет.
5. Для MVP допустима простая админская настройка пользователей через seed/config/CLI, без отдельной админ-панели.
6. Сначала делаем устойчивую 1:1 переписку и 1:1 звонок, затем групповые функции.

## Основные доменные сущности

- User — заранее созданный пользователь.
- Device — конкретное устройство пользователя с публичными ключами.
- Session — авторизованная сессия.
- Chat — личный или групповой чат.
- ChatMember — участник чата.
- Message — метаданные сообщения и шифротекст.
- Attachment — метаданные зашифрованного файла.
- Call — звонок.
- CallParticipant — участник звонка.
- PreKeyBundle — набор ключей устройства для установки E2EE-сессии.

## Основные протоколы взаимодействия

### REST

REST используется для логина, загрузки профиля, списка чатов, истории сообщений, загрузки/скачивания вложений через pre-signed URLs, управления участниками групп и обмена публичными ключами устройств.

### WebSocket

WebSocket используется для realtime-событий: новые сообщения, доставка/прочтение, typing indicator, online/offline, signaling для WebRTC, изменение состояния звонка.

### WebRTC

- 1:1 звонки — peer-to-peer, если сеть позволяет.
- Если прямое соединение невозможно — relay через COTURN.
- Групповые звонки в MVP — mesh WebRTC для небольшого числа участников.
- При росте нагрузки — отдельный SFU, например LiveKit или mediasoup.

## Ограничения MVP

- Android-only.
- До 10 активных пользователей.
- Без публичной регистрации.
- Без web-клиента.
- Без полноценной админ-панели.
- Без federation и внешних интеграций.
- Групповые звонки ограничить малым числом участников, например до 4, если используется mesh.

## Нефункциональные требования

- Все внешние соединения только через TLS.
- Пароли хранятся только в виде Argon2id-хешей.
- Access token короткоживущий, refresh token хранится безопасно.
- Backend логирует технические события, но не plaintext сообщений.
- Docker Compose должен поднимать всю серверную часть одной командой.
- Секреты не хранятся в git.
